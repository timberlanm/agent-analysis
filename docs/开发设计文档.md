# 第一部分 · 数据模型

> 存储：**SQLite** 单文件 `backend/data/analysis_store.db`（首次运行自动创建）。对齐 `init_db()` 建表语句。

### 0. 通用约定

- **主键 `id`**：全部为 `TEXT`，由 `_id(prefix)` 生成（前缀 + 随机十六进制），如 `alt_xxx`（告警）、`att_xxx`（附件）。
- **时间字段**：全部为 `TEXT`，存 ISO8601 字符串（`created_at` / `updated_at` / `occurred_at` 等）。
- **JSON-in-TEXT**：部分字段存 JSON 字符串（下表注明），读取时反序列化。
- **外键**：子表 `alert_id` → `alerts(id)`，`ON DELETE CASCADE`（删除告警级联删除其附件/实体/备注/子任务等）。
- **无软删除**：删除即物理删除。
- **审计**：写操作经 `_audit(...)` 落 `audit_logs`。

### 9. 枚举值

| 枚举 | 值（key → 中文） |
|------|------------------|
| 告警状态 `status` | new 新建中 / pending 待分配 / assigned 已分派 / triaging 初筛中 / investigating 研判中 / responding 应急响应中 / need_info(=waiting_info) 待补充信息 / confirmed 已确认 / closed 已完成 / escalated 已升级事件 |
| 研判结论 `conclusion` | false_positive 告警误报 / business 正常业务 / true_positive 真实攻击 / incident 安全事件 / unknown 无法确认 |
| 严重程度 `severity` | critical / high / medium / low / info |
| 子任务状态 | todo 待处理 / doing 处理中 / done 已完成 |
| 设备类型 `source_category` | edr / hids / ndr / waf / siem / other |

> 主生命周期只用其中 5 个状态：new → pending → investigating → responding → closed（其余状态为枚举保留/细分场景）。
> 结论派生集合：`INCIDENT_CONCLUSIONS = {true_positive, incident}`（事件类）；`AUTO_RESPONDING_CONCLUSIONS = {incident}`（仅此自动转应急）。详见第三部分。

### 10. `normalized_fields` 规范字段集（JSON 对象）

归一化后的统一字段键（`_normalize_alert` 产出，前端「告警详情」按此渲染）：

```
source_ip, destination_ip, source_port, destination_port,
hostname, username, domain, url, file_hash, file_path,
process_name, command_line, rule_name, rule_id,
protocol, http_method, http_status, user_agent, event_action
```

- 研判员可增补**任意自定义键**（经 `update_alert` 的 `custom_fields` 通道写入，键名不受上表限制）。
- 每个规范键由一串候选别名匹配得到（如 `source_ip` ← src_ip/sip/attacker_ip/client_ip）。

### 11. ER 关系概览

```
alerts (1) ──< attachments        (alert_id, CASCADE)
       (1) ──< entities           (alert_id, CASCADE, 唯一去重)
       (1) ──< notes              (alert_id, CASCADE, 按 round 分轮)
       (1) ──< subtasks           (alert_id, CASCADE)
       (1) ──< assignment_logs    (alert_id, CASCADE)
       (1) ──< escalation_records (alert_id, CASCADE)

audit_logs  ── 独立（按 target_type/target_id 弱关联，无外键、不级联）
```

# 第二部分 · API 接口清单

> 对齐 `backend/api/incident.py`。基础路径前缀：**`/api/incident`**（例：`GET /api/incident/alerts`）。

### 0. 通用约定

- **协议**：HTTP / JSON。
- **响应包**：成功 `{"success": true, "data": <...>}`；失败 `{"success": false, "error": "<消息>"}`。
- **状态码**：`200` 成功；`400` 业务错误（校验失败等，`error` 含原因）；`404` 资源不存在。
- **操作者身份**：由 `_actor()` 解析——请求头 `X-User`，或查询参数 `?actor=`，缺省 `"operator"`。
  ⚠️ **当前无认证、无权限校验**（任何调用者可访问任何接口）。RBAC 落地时应替换为登录会话身份，并加统一鉴权。
- **写操作**均记入 `audit_logs`。

# 第三部分 · 研判处理状态机规格

> 对齐 `set_status` / `set_conclusion` / `set_handlers` / `reject_alert` / `reopen_alert` / 完成门控。规则默认由**后端强制**；标注「前端」者为前端交互约定。

### 1. 三个耦合属性 + 轮次

一条告警的研判进度由三要素联动，外加轮次计数：

| 属性 | 字段 | 取值 |
|------|------|------|
| 状态 | `status` | 见下（主用 5 态） |
| 结论 | `conclusion` | false_positive/business/true_positive/incident/unknown，可空（未定） |
| 处理人 | `handlers`（JSON 数组） | 当前研判员/处置人；无独立"处置人"字段 |
| 轮次 | `round` | 初始 1，每次闭环回流 +1 |

**状态（主生命周期）**：
```
new 新建中 → pending 待分配 → investigating 研判中 → responding 应急响应中 → closed 已完成
```
（枚举另含 assigned/triaging/need_info/confirmed/escalated 等细分态，主流程不用。）

**结论派生集合**（勿混用）：
- `INCIDENT_CONCLUSIONS = {true_positive, incident}` —— 事件类，与「应急响应中」语义兼容（进 responding 不被作废）。
- `AUTO_RESPONDING_CONCLUSIONS = {incident}` —— **仅「安全事件」自动转应急**。「真实攻击」不自动跳（可能未遂/未成规模），留在研判中，需要时人工转应急或直接挂处置子任务。

### 2. 状态迁移图

```
                     创建(create_alert)
                          │ 默认
                          ▼
   ┌──────────┐   指派处理人   ┌──────────────┐  结论=incident(自动)  ┌──────────────┐
   │ pending  │──────────────►│ investigating│──────────────────────►│ responding   │
   │ 待分配   │  set_handlers  │   研判中     │   set_conclusion       │ 应急响应中   │
   └──────────┘               └──────┬───────┘                        └──────┬───────┘
        ▲                            │  完成(补全依据+建议)                   │ 完成
        │                            └──────────────┬─────────────────────────┘
        │ 驳回重判(reject)                          ▼
        │ round+1,清空                        ┌──────────┐
        └─────────────────────────────────────│ closed   │
                重新指派(set_handlers)          │ 已完成   │
                round+1 → investigating ◄───────└────┬─────┘
                重新研判(reopen)                     │
                round+1 → investigating/responding ◄─┘
```

### 3. 触发器与规则（逐条）

**3.1 创建告警 `create_alert`**
- 初始 `status` = 入参 `status`，缺省 **`pending`**；`conclusion` 缺省空；`round=1`。

**3.2 指派处理人 `set_handlers`（PUT `/handlers`）**
覆盖 `handlers` 集合，并按原状态自动流转：
- **pending + 有新处理人** → 自动进入 **investigating**（"指派处理人后自动进入研判"）。
- **closed + 有新处理人**（重新指派重开）→ `round+1`，**清空** `conclusion / close_reason / key_evidence / evidence_info / handling_suggestion`，进入 **investigating**，带入新处理人。
- 其他状态：仅更新处理人集合，不改状态。
- 增删处理人各记一条 assignment 备注。

> `assign_handler`/`remove_handler`（POST/DELETE `/handlers`）为单个增删，不触发上述自动流转。

**3.3 设置结论 `set_conclusion`（POST `/conclusion`）**
- 写入 `conclusion`，记一条 conclusion 备注。
- **若 `conclusion=incident` 且当前状态 ∉ {closed, responding}** → 自动 `set_status(responding)`（"安全事件自动转应急响应处置"）。
- 其他结论不改状态。

**3.4 切换状态 `set_status`（POST `/status`）**
- **校验**：`status` 必须是合法枚举，否则报错。
- **禁止回跳**：`closed → 非 closed` 直接改状态被拒绝（"请用『重新指派』或『驳回重判』重开"）。
- **→ closed（完成门控）**：校验**研判依据 `key_evidence`** 与**处置建议 `handling_suggestion`** 两项非空（有效值 = 本次入参或库中现值），缺失则报错 `完成前请补全：…`。可同时带入 conclusion/key_evidence/handling_suggestion/close_reason（仅显式提供才更新）。
- **→ responding（结论-状态一致性，软处理）**：若当前 `conclusion` 为**非事件类**（∉ INCIDENT_CONCLUSIONS，即误报/正常业务/无法确认）→ **作废为空（未定）**并记一条说明备注，留待重新研判。
- 每次切换记一条 status_change 备注。

**3.5 驳回重判 `reject_alert`（POST `/reject`）**
- **前置**：仅 `closed` 可驳回。
- 效果：→ **pending**；**清空** `conclusion / close_reason / handlers([]) / key_evidence / evidence_info / handling_suggestion`；`round+1`；记 status_change 备注。

**3.6 重新研判 `reopen_alert`（POST `/reopen`）**
- **前置**：仅 `closed`；必须给出合法 `conclusion`。
- 效果：改判 `conclusion`；→ **responding**（若结论 ∈ AUTO_RESPONDING）否则 **investigating**；**保留当前处理人**；`round+1`；`close_reason` 清空。
- **研判三项快照不在后端清**——由前端归档软清空（见 4.2）。

### 4. 两个"软清空"机制

**4.1 转应急作废非事件结论（后端，见 3.4）**
进入 responding 时，非事件类结论被作废为空——**只清不伪造**，不自动写具体结论，留待重研。

**4.2 结论翻转软清空（前端 `archiveAndSoftClear`）**
在活动态直接改结论（A→B）或 closed 重新研判且已有研判内容时：
- 旧研判三项整段**归档进研判记录**；
- **处置建议**强耦合**清空**；**研判依据/举证**标记**待复核**（保留原值，可沿用或清空重填）。

### 5. 完成门控（Definition of Done）

置为 `closed` 前，必须满足：
- `key_evidence`（研判依据，含举证）非空；
- `handling_suggestion`（处置建议）非空。

（`evidence_info` 举证信息已并入研判依据、退出门控；列保留存历史。）

### 6. 不变量（Invariants）

1. **closed 是保护态**：不能直接改状态离开，只能经 重新指派 / 驳回重判 / 重新研判 三个入口重开，且均 `round+1`。
2. **responding ⇒ 结论非"非事件类"**：进入 responding 会作废矛盾的非事件结论。
3. **完成 ⇒ 依据与建议齐全**（门控）。
4. **仅 incident 自动转 responding**；true_positive 不自动跳。
5. **每个结论都要有对应处置**（handlers/子任务），无"无需处置"旁路。
6. **闭环全程留痕**：状态/结论/指派/驳回/重研均写 notes（按 round 分轮）与 audit_logs。
